# Module 9 — Processes, jobs, priorities, and scheduling

> **Exam objective:** Linux+ 2.3 — Given a scenario, manage and troubleshoot
> processes and jobs.
> **Study time:** about 100 minutes, including the mission.
> **Mission:** `proc_audit.py` plus a `cron.d/backup` schedule — triage a
> process snapshot and schedule a real backup job.

## What the exam expects

Every process question reduces to four things: how a process is created, what
state it is in, who owns it, and what it is waiting for. You must know:

- `/proc` as the live process and kernel interface,
- `ps`, `top`, `pgrep`, `pstree`, `strace`, `lsof`, `lsof -p`,
- process states (`R`, `S`, `D`, `T`, `Z`, `I`),
- nice values, `nice`, `renice`, `ionice`,
- `ulimit` and `/etc/security/limits.conf`,
- foreground/background jobs, `jobs`, `fg`, `bg`, `Ctrl-Z`, `&`, `nohup`,
- signals: `SIGTERM`, `SIGKILL`, `SIGHUP`, `SIGINT`, `SIGSTOP`/`SIGCONT`,
- scheduling: `cron`, `crontab`, `/etc/cron.d`, `anacron`, `at`,
  `systemd` timers (module 10).

## `/proc` — the process filesystem

Each process gets a directory named by PID:

```bash
ls /proc/1234
cat /proc/1234/status      # Name, State, Uid, Gid, Threads, VmRSS
cat /proc/1234/cmdline | tr '\0' ' '; echo
readlink /proc/1234/cwd    # working directory
readlink /proc/1234/exe    # executable path
ls -l /proc/1234/fd        # open file descriptors
cat /proc/1234/environ | tr '\0' '\n'
cat /proc/1234/limits
```

System-wide files worth knowing:

| Path | Meaning |
|---|---|
| `/proc/loadavg` | 1/5/15-minute load average and runnable count |
| `/proc/meminfo` | memory and swap detail |
| `/proc/cpuinfo` | CPU model, flags, per-core info |
| `/proc/uptime` | seconds since boot and idle seconds |
| `/proc/<pid>/oom_score` | how likely the OOM killer is to pick it |

`/proc` is not on disk. It is generated by the kernel on read, which is why
`ls -l /proc/<pid>` shows size 0 for most files.

## Reading `ps`

```bash
ps aux                 # BSD style: every process, user-oriented
ps -ef                 # System V style: full listing with PPID
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head
ps -u alice
ps -p 1234 -o pid,stat,wchan:30,cmd
```

Columns that matter:

- `PID` — process id; `PPID` — parent process id.
- `STAT` — state plus modifiers.
- `%CPU` / `%MEM` — share of CPU and resident memory.
- `TIME` — cumulative CPU time, not elapsed time.
- `WCHAN` — kernel function the process is sleeping in (great for `D` state).
- `NI` — nice value.

### Process states

| Code | State | Meaning |
|---|---|---|
| `R` | running/runnable | on CPU or waiting for a turn |
| `S` | interruptible sleep | waiting for an event; normal |
| `D` | uninterruptible sleep | waiting on I/O; cannot be killed |
| `T` | stopped | `Ctrl-Z` or `SIGSTOP` |
| `Z` | zombie | exited, parent has not reaped it |
| `I` | idle | kernel thread with no work |

Modifiers: `s` session leader, `l` multi-threaded, `+` foreground process
group, `<` high priority, `N` low priority.

### Zombies and `D` state

A **zombie** has finished but its parent has not called `wait()`. It holds a
PID and a process-table entry but no memory. You cannot kill a zombie; you fix
the parent (restart or signal it) or reboot. Many zombies usually mean a buggy
daemon.

A process in **`D`** is stuck in a kernel call, typically I/O. `kill -9` does
not work until the I/O returns. A pile of `D` processes means storage or NFS is
unhealthy. Check `dmesg` and `iostat`.

## `top`, `htop`, and friends

```bash
top
# inside top: P sort by CPU, M by memory, 1 per-core, k kill, r renice
top -b -n 1 -o %CPU | head -20
htop
```

`top`'s header shows load average, tasks by state, CPU breakdown (`us`, `sy`,
`wa` for I/O wait, `id` idle, `si`/`hi` interrupts), and memory/swap. High
`wa` with low `us` points at storage, not CPU.

## Process trees and tracing

```bash
pstree -p
pstree -p 1234
pgrep -a nginx
pgrep -u alice -l
pstree -p | grep bash
```

`pstree` shows parent/child relationships, which is how you answer “which
service started this process?”. `pgrep -a` prints PID and command line.

`strace` shows the syscalls a process makes:

```bash
strace -p 1234 -f -e trace=network
strace -c ls /tmp
strace -o trace.log ./app
```

It is the tool for “the process hangs and I do not know why”. `-f` follows
children, `-e` filters, `-c` summarises counts.

## Priorities: nice and ionice

The scheduler uses a **nice** value from -20 (most favourable) to 19 (least).
Only root can lower a nice value.

```bash
nice -n 10 tar -czf /backup/app.tar.gz /srv/app
renice -n 5 -p 1234
renice -n 10 -u alice
ionice -c3 -p 1234          # idle I/O class
ionice -c2 -n7 ./backup.sh  # best-effort, low priority
```

```bash
ps -eo pid,ni,cmd --sort=ni | head
```

Nice affects CPU scheduling only. `ionice` affects block I/O. A backup job can
be harmless to CPU and still saturate the disk — use both.

## Limits: `ulimit`

```bash
ulimit -a
ulimit -n              # open files
ulimit -n 4096         # raise in this shell (soft limit)
ulimit -Hn             # hard limit
```

Per-user persistent limits live in `/etc/security/limits.conf` or
`/etc/security/limits.d/*.conf`:

```
alice   soft   nofile   4096
alice   hard   nofile   8192
*       soft   nproc    2048
```

Systemd services need `LimitNOFILE=` in the unit (module 10); `limits.conf` is
applied by PAM for login sessions, not by the service manager.

## Job control

```bash
sleep 300 &            # background job
jobs -l
fg %1
bg %1
Ctrl-Z                 # suspend foreground job
Ctrl-C                 # SIGINT to foreground group
nohup ./long-job > out.log 2>&1 &
disown %1
```

A job lives in the shell that started it. Closing the terminal sends `SIGHUP`
to the shell's jobs. `nohup` ignores `SIGHUP`; `disown` removes the job from
the shell's table so it is not signalled. Use `tmux` or `screen` for anything
longer than a few minutes over SSH.

## Signals

```bash
kill -l                  # list signals
kill -TERM 1234
kill -HUP 1234           # often "reload configuration"
kill -9 1234             # SIGKILL, cannot be caught
kill -STOP 1234
kill -CONT 1234
pkill -f 'python.*worker'
killall nginx
```

Signal behaviour:

| Signal | Number | Typical effect |
|---|---|---|
| `SIGHUP` | 1 | hangup / reload for many daemons |
| `SIGINT` | 2 | `Ctrl-C`, interrupt |
| `SIGQUIT` | 3 | quit with core dump |
| `SIGKILL` | 9 | immediate kill, no cleanup |
| `SIGTERM` | 15 | polite termination, the default |
| `SIGSTOP` | 19 | stop, cannot be caught |
| `SIGCONT` | 18 | continue a stopped process |
| `SIGCHLD` | 17 | child state change, delivered to parent |

Always try `SIGTERM` first. `SIGKILL` skips cleanup, can corrupt data, and does
not work on `D` state or zombies.

## Scheduling with cron

`cron` runs commands on a schedule. There are three places jobs live:

| Location | Format |
|---|---|
| user crontab (`crontab -e`) | 5 time fields + command |
| `/etc/crontab` | 5 time fields + **user** + command |
| `/etc/cron.d/<name>` | 5 time fields + **user** + command |
| `/etc/cron.daily/` etc. | scripts run by `anacron`/`run-parts` |

```
# .---------------- minute (0-59)
# |  .------------- hour (0-23)
# |  |  .---------- day of month (1-31)
# |  |  |  .------- month (1-12)
# |  |  |  |  .---- day of week (0-7, Sunday = 0 or 7)
# |  |  |  |  |
  15 2  *  *  *  root  /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
```

Special strings: `@reboot`, `@daily`, `@weekly`, `@monthly`, `@yearly`.
`*/5` means every five units; `1-5` is a range; `1,15` is a list.

Rules that prevent real incidents:

- cron has a minimal environment: set `SHELL=/bin/bash` and a full `PATH` at
  the top of `/etc/cron.d` files.
- redirect both stdout and stderr or you will get mail (or silence).
- cron jobs must be executable and must not depend on your shell profile.
- test the command manually as the same user first.
- `/etc/cron.d` files must be root-owned and not group/world-writable, or cron
  ignores them.

```bash
crontab -l
crontab -e
crontab -u alice -l
```

### `at` for one-shot jobs

```bash
echo '/usr/local/bin/backup.sh' | at 02:15
at -l
atrm 3
```

`atd` must be running. `batch` runs when load is low.

### `anacron`

`anacron` runs missed jobs on machines that are not always on. It reads
`/etc/anacrontab` and records timestamps in `/var/spool/anacron/`. The
`/etc/cron.daily` directories are usually driven by `anacron` through
`run-parts`, not directly by `cron`.

## Diagnosing a missing cron job

1. `systemctl status crond` (RHEL) or `cron` (Debian).
2. Check the file is in the right place and has the right field count.
3. Check ownership/mode of `/etc/cron.d/*` (must be root-owned, not writable by
   others).
4. Check `/etc/cron.allow` and `/etc/cron.deny`.
5. Look at the logs: `journalctl -u crond` or `/var/log/cron`.
6. Run the command manually with `env -i` to simulate cron's environment.

## Exam traps

- `%CPU` in `ps` is an average over the process's lifetime; `top` shows a
  recent sample.
- A zombie cannot be killed. Fix the parent.
- `D` state ignores `SIGKILL`.
- `nice` affects CPU, `ionice` affects I/O.
- `limits.conf` does not apply to systemd services.
- `/etc/cron.d` needs the user field; a user crontab does not.
- cron does not read `~/.bashrc`; export what you need in the job.
- `kill -9` first is a bad habit that causes data loss.
